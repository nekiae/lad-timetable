## 2. Откуда взялась идея (первоисточник боли)

Личный опыт: в школе расписание появлялось **примерно на второй неделе учёбы**,
потому что завуч постоянно его переставляла. Требования, которые она пыталась
совместить одновременно:

- все часы учебного плана должны быть выданы;
- классам должно быть удобно (нет окон, нормальная нагрузка по дням);
- соблюдены санитарные нормы;
- учителю удобно: уроки в разных классах идут подряд, нет «форточек»,
  не надо приезжать в школу ради одного урока.

И **всё равно получалось не идеально.**

Это подлинная, воспроизводимая, массовая боль. Проблема не в том, что боли нет.

**Опенсорс / движки:** FET, UniTime (Purdue), Timefold/OptaPlanner,
**Google OR-Tools CP-SAT** ← наш выбор.

### 3.2. Алгоритмическая часть — решённая задача

School timetabling — классическая **NP-трудная задача комбинаторной оптимизации**,
изучается ~60 лет. Есть International Timetabling Competition (ITC), десятки
диссертаций, готовые солверы. Расписание школы на ~30 классов CP-SAT решает
за секунды-минуты на ноутбуке.

**Критично понимать: LLM здесь почти ни при чём.** Жёсткие ограничения решает
солвер, а не нейросеть. «AI-расписание» в маркетинге 2026 — обычно обёртка над
тем же constraint solver. Поэтому «применим ИИ и получим идеал» **не является**
технологическим преимуществом — оно есть у всех.

Единственное осмысленное место для LLM в этом проекте — **сбор ограничений
из живой речи завуча** и превращение их в формальные constraints (см. §5).

### 3.3. Почему тогда завуч всё равно страдает две недели

Причина НЕ в отсутствии алгоритма. Реальные причины:

1. **Ввод данных.** Чтобы солвер заработал, надо формализовать нагрузку, деления
   на подгруппы, совместительство, кабинетный фонд, пожелания 60 учителей.
   Это **~80% работы**, и её никто не автоматизировал.
2. **Ограничения живут в голове завуча**, а не на бумаге: «Иванова по вторникам
   не может», «химию нельзя после физры», «у Петровой ребёнок в саду».
3. **Расписание не составляется один раз.** Больничные, замены, курсы, изменение
   нагрузки в сентябре. **Ежедневные замены — боль больше, чем стартовая сборка**,
   и именно на ней зарабатывает Untis.
4. **Оно не должно быть оптимальным — оно должно быть согласованным.** Идеальное
   по метрике расписание, где обиделись три учителя, хуже неидеального,
   где не обиделся никто.
5. **Локальные санитарные нормы РБ** импортные Untis/aSc не знают,
   а «Ректор» настраивается вручную под российский СанПиН.

**→ Настоящая дельта продукта: не солвер, а ввод данных + локальные нормы +
замены + объяснимость («почему нельзя иначе» — чтобы завуч мог спорить
с учителем ссылкой на систему).**

Если проект переживёт точку выхода, продукт выглядит так:

4. **Модуль замен** — ежедневная боль, приоритетнее стартовой сборки.
   Учитель заболел → система за секунды предлагает варианты замен с обоснованием.
5. **Объяснимость** — на любой вопрос «почему так?» система показывает, какие
   ограничения нарушатся при перестановке. Это оружие завуча в разговоре с учителями.

Позиционирование: **не «система для школ», а модуль расписания для «Электронной школы».**

### 5.1. Эволюция формата (куда растём после MVP)

Один HTML-файл — это формат **демо**, а не потолок системы. Разделение
`солвер → schedule.json → рендер` (§7.1) существует ровно для того, чтобы
менять способ показа, не переписывая ядро. Порядок роста:

| Этап | Формат | Что добавляет | Когда |
|---|---|---|---|
| 0 | CLI → HTML-файл | демо, пересылается в мессенджер | эта неделя |
| 1 | + Excel/CSV-экспорт | завуч кладёт результат в свой рабочий процесс | по первому запросу школы |
| 2 | Веб-приложение (FastAPI + фронт) | загрузка нагрузки, ручная правка сетки с живой проверкой ограничений, объяснимость (§5.5) | только после точки выхода §10 |
| 3 | HTTP-API как модуль | «Электронная школа» дёргает солвер у себя | сценарий подряда с ГИАЦ (§4.3) |

Ключевое: этап 3 — это тот же солвер за HTTP-ручкой. Ядро на CP-SAT не переделывается
ни на одном из переходов, меняется только оболочка. Поэтому ранний выбор «файл вместо
веб-приложения» ничего не закрывает в будущем — он только убирает 3 дня работы
из недели, которой и так нет.

⚠️ Этапы 1–3 **не начинаются** до прохождения §10. Это и есть тот самый
зомби-проект, против которого написан §6.

### 7.1. Стек и формат системы (РЕШЕНО 21.08.2026)

- **Python 3.13** (у ortools пока нет колёс под 3.14), venv в `.venv/`
- **ortools** (CP-SAT solver) — ядро
- **pandas** — работа с данными
- Никакого React, бэкенда, БД и деплоя (§6).

**Формат MVP: CLI-скрипт, который отдаёт один самодостаточный HTML-файл.**

```
python -m lad.solve data/school.xlsx  →  out/raspisanie.html
```

Пайплайн жёстко разделён на три звена — это главное архитектурное решение проекта:

```
вход (нагрузка) → [СОЛВЕР] → schedule.json → [РЕНДЕР] → HTML
```

Солвер ничего не знает про то, как расписание показывают. Рендер ничего не знает
про то, как оно получено. Между ними — только `schedule.json`.

**Почему один HTML-файл:**
- Демо надо будет не только показать за ноутбуком, но и **переслать** («пришлите»).
  Файл переживает оба сценария, запущенный процесс — только первый.
- Стили и данные внутри, внешних запросов нет, открывается двойным кликом,
  читается с телефона.
- Сломанная вёрстка не блокирует солвер: день 6 можно переверстать за час,
  не трогая логику.

**Что внутри HTML:** сверху три цифры «было/стало» (окна, нарушения норм, время),
ниже сетка класс × день, ховер на уроке = учитель + кабинет, переключатель
«реальное расписание школы / наше». JS только на переключатель, библиотек нет.

**Streamlit** — не демо, а **инструмент отладки для себя** на дне 4, когда
подбираются веса штрафов. Зрителю не показывается, в поставку не входит.

**Отклонено для MVP:** веб-приложение с бэкендом (запрет §6, минус 3 дня),
Excel-выгрузка как основной вывод (нужна на фазе продукта, но три цифры
в таблице не бьют). Путь развития форматов — §5.1.

### 7.2. Что такое CP-SAT (объяснение для вайбкодера)

Представь, что у тебя есть сетка: класс × день × номер урока. В каждую клетку надо
положить пару (предмет, учитель). Вручную ты бы перебирал варианты и откатывался,
когда что-то не сходится.

**CP-SAT** — это движок, которому ты не пишешь «как искать». Ты описываешь только:
- **переменные** — что мы ищем (какой урок в какой клетке);
- **hard constraints** (жёсткие ограничения) — что запрещено абсолютно
  («учитель не может быть в двух классах одновременно»);
- **soft constraints** (мягкие) — что нежелательно, но допустимо
  («окно у учителя — это плохо, штраф 10 очков»);
- **целевую функцию** — что минимизируем (сумму штрафов).

Дальше солвер сам перебирает миллиарды вариантов умным способом и выдаёт лучший
найденный. Твоя работа — **правильно описать ограничения**, а не писать алгоритм.

### 7.3. Модель данных (минимальная)

```
Класс:      id, параллель (1-11), количество учеников
Учитель:    id, ФИО, предметы, недопустимые слоты (когда не может)
Предмет:    id, название, ранг трудности (по шкале), нужен_кабинет
Кабинет:    id, тип (обычный/физика/химия/спортзал/компьютерный), вместимость
Нагрузка:   класс + предмет + учитель + часов_в_неделю   ← ГЛАВНАЯ ТАБЛИЦА
Слот:       день (1-6) × номер урока (1-8)
```

Выход: `Расписание: слот → (класс, предмет, учитель, кабинет)`

### 7.4. Ограничения

**HARD (нарушать нельзя):**
1. Учитель не ведёт два урока одновременно.
2. Класс не имеет двух уроков одновременно.
3. Кабинет не занят дважды одновременно.
4. Все часы из таблицы нагрузки выданы ровно в нужном количестве.
5. Предмет требующий спецкабинета ставится только в него.
6. Учитель не ставится в свои недопустимые слоты.
7. Не превышена максимальная дневная/недельная нагрузка класса (санитарные нормы).
8. У класса нет окон (в школе класс учится подряд).
9. **Подгруппы одного деления идут синхронно, в один слот.** Иначе полкласса
   ждёт, пока вторая половина учится. Найдено на hello-world 21.08.2026,
   см. docs/domain.md §4.7.

**SOFT (минимизируем штрафы):**
1. Окна у учителей — большой штраф.
2. Уроки учителя в один день собраны компактно (не 1-й и 7-й).
3. Учитель приходит в школу минимальное число дней в неделю.
4. Трудные предметы не ставятся первым и последним уроком.
5. Равномерная недельная нагрузка класса по дням (нет дня с 8 уроками
   и дня с 3).
6. Пик сложных предметов приходится на вторник–среду (динамика работоспособности).
7. Не более одной контрольной в день у класса.
8. Физкультура не перед сложным предметом / не последней парой подряд с трудным.

### 7.5. Санитарные нормы РБ — ⚠️ ТРЕБУЮТ ПРОВЕРКИ ПО ПЕРВОИСТОЧНИКУ

Базовый документ: **Санитарные нормы, правила и гигиенические нормативы
«Требования для учреждений общего среднего образования»,
утв. постановлением Минздрава РБ от 27.12.2012 № 206** (с изменениями).

Что известно и надо оцифровать:
- **Ранговая шкала трудности учебных предметов** — есть научно обоснованная шкала
  для 5–9 классов (публикация БГМУ). Нужны точные ранги по каждому предмету.
- Расписание составляется с учётом **дневной и недельной динамики работоспособности**.
- Чередование предметов со значительным умственным и статическим напряжением
  с предметами, включающими двигательный и динамический компонент.
- Максимальная допустимая недельная нагрузка по параллелям — **уточнить цифры**.
- Ограничения на сдвоенные уроки — **уточнить**.

**ЗАДАЧА ДЛЯ CLAUDE CODE:** найти PDF первоисточника (adu.by, edu.gov.by,
или PDF на сайтах школ/райисполкомов), извлечь точные таблицы и положить в
`data/sanpin_by.json`. НЕ выдумывать цифры. Если цифра не подтверждена —
помечать `"source": "UNVERIFIED"` и выносить в открытые вопросы.

⚠️ Сайты `edu.gov.by`, `giac.by`, `schools.by`, `adu.by` могут не открываться
с зарубежных IP. Если WebFetch падает с ECONNREFUSED — искать зеркала,
PDF на сайтах отдельных школ, или просить Влада открыть вручную.

### 8.1. Данные: реальное расписание школы Влада — критический путь ДНЯ 1

**РЕШЕНО 21.08.2026: никаких запросов в ГИАЦ/Минобр до готового MVP.**
Первый зритель демо — **завуч школы Влада** (личный контакт, хорошие отношения).
Госконтур (§8.6) — только после того, как завуч вынесет вердикт.

Почему это правильнее прежнего плана: чиновник скажет «интересно, пришлите на почту».
Завуч — единственный человек, способный сказать **«вот это неправда, так расписание
не ставят»**. Это единственная настоящая проверка работоспособности, и она бесплатна.

#### Что именно нужно достать — и почему это одно и то же

Нужно **реальное расписание школы**, а не таблица нагрузки. Причина в том, что оно
закрывает сразу две дыры:

1. **Нагрузка выводится из него автоматически.** Посчитал по сетке, сколько раз
   в неделю у 7«Б» стоит физика с Ивановым — вот и часы. Это вход для солвера.
2. **Это наше «было».** Без реального расписания сравнивать не с чем и три цифры
   демо (§6) не существуют. Синтетика этого не даёт **в принципе**.

Поэтому §7.6 вариант 3 (реверс-инжиниринг из опубликованного расписания) —
не запасной путь, а **основной**. И у него есть бонус: расписание школы обычно
висит публично, значит на этом этапе **вообще ни у кого ничего не надо просить**.
Завуч увидит готовое демо на данных своей школы без единого предупреждения.

#### Как достать (делает Влад лично, сегодня)

⚠️ Сайты `.by` отдавали ECONNREFUSED 21.08.2026 — автоматически не заберём.
Влад открывает вручную и сохраняет в `data/raw/`:
- schools.by → страница своей школы → раздел расписания;
- либо сайт школы напрямую (часто PDF или Word);
- либо фото/скрин расписания — распарсим глазами модели.

Нужен максимум: **все классы, все дни, все уроки, с учителями**. Если учителей
в публичной версии нет — сказать сразу, модель придётся строить иначе (см. §8.5).

#### Если публичного расписания нет

Тогда — попросить у завуча выгрузку напрямую, но **без питча и без обещаний**:
«делаю учебный проект по составлению расписаний, дай пример реального —
на нём проверю алгоритм». Это не тот разговор, который тратит контакт.
Настоящий разговор с демо — на дне 7.

### 8.2. Что спросить у завуча вместе с демо (день 7)

Демо без правильного вопроса — просто картинка. Вопросы задавать **фактические**,
а не оценочные («нравится?» — все говорят «да»):

1. **Это расписание можно поставить в работу или нет? Если нет — что первое сломается?**
   ← главный вопрос, ради него всё делается
2. Что здесь неправильно с точки зрения школы, чего алгоритм не знает?
3. Сколько дней ушло у вас на это расписание руками?
4. Что больнее — собрать в августе или разруливать замены каждый день?
5. Если бы такое работало — кто в школе решает, покупать или нет?

Ответ на 2 — это техзадание на следующую итерацию. Ответ на 1 — это точка выхода §10.

### 8.3. Честность сравнения — жёсткое правило

Метрики «было» и «стало» считает **один и тот же валидатор**, один и тот же код,
на одной и той же структуре данных. Никаких «для нашего считаем так, для школьного
иначе». Иначе сравнение — враньё, и первый же вопрос завуча его вскроет.

Валидатор — отдельный модуль, который принимает `schedule.json` и возвращает
список нарушений. Наше расписание и школьное приводятся к одному формату
**до** подсчёта.

### 8.4. Персональные данные — учесть до контента

В расписании школы **настоящие ФИО учителей**. Для завуча это нормально и нужно
(он должен узнать своих). Для блога, видео и любого показа третьим лицам —
**обязательная анонимизация**: ФИО → «Учитель 1», номер школы убрать.

Держать два выхода: `out/raspisanie.html` (реальные имена, только завучу)
и `out/raspisanie_public.html` (обезличенный). Флаг `--anonymize`.

### 8.5. Чего в публичном расписании не видно (главные ловушки модели)

Реверс-инжиниринг даёт не всё. Заранее известные дыры:

| Чего не видно | Чем грозит | Что делаем на MVP |
|---|---|---|
| **Деление на подгруппы** (языки, физра, труд) | ломает базовую модель «класс = один урок в слот»: две подгруппы учатся одновременно у разных учителей | распознать по сетке (два урока в одном слоте у одного класса) и завести подгруппы явно. **Пропустить нельзя — завуч заметит первым** |
| Кабинетный фонд | HARD-3 (кабинет не занят дважды) не проверить | на MVP оставить только спецкабинеты, которые выводятся из предмета (физра→спортзал, информатика→компьютерный). Остальное — `UNVERIFIED` |
| Совместители (работают в 2 школах) | учитель «свободен», хотя физически в другой школе | не моделируем, помечаем как известное ограничение демо |
| Личные пожелания учителей | наше расписание формально лучше, а по-человечески хуже | не моделируем. Это **честный ответ на вопрос завуча**, а не дыра, которую надо прятать |

**Правило:** каждую такую дыру озвучивать самому, до того как её найдёт завуч.
Демо, автор которого знает границы своей модели, вызывает доверие.
Демо, которое делает вид, что учло всё, разваливается от первого вопроса.

   и пригодится в ND BOT и других белорусских затеях.
4. **Скилл.** Constraint solving — редкая компетенция, которой не научишься вайбкодингом.

## 13. Глоссарий

- **ЛАД** — название проекта: Логистика Академического Дня. По-белорусски «лад» —
  порядок, склад, гармония («наладить»). Выбрано за локальность: это аргумент
  против импортных Untis/aSc и опора на стратегию §4.3.
- **Timetabling** — задача составления расписания; класс NP-трудных задач.
- **CP-SAT** — constraint programming solver из Google OR-Tools.
- **Hard constraint** — жёсткое ограничение, нарушение недопустимо.
- **Soft constraint** — мягкое, нарушение штрафуется в целевой функции.
- **Целевая функция** — то, что минимизируем (сумма штрафов).
- **Окно / форточка** — свободный урок в середине рабочего дня учителя.
- **Нагрузка (тарификация)** — сколько часов какого предмета в каком классе
  ведёт какой учитель. Главный вход для солвера.
- **Замены** — оперативная перестройка при отсутствии учителя.
- **ГИАЦ** — Главный информационно-аналитический центр Минобразования РБ,
  разработчик «Электронной школы».
